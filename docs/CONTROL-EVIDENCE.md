# Compliance controls: description, test, and evidence

Reviewed October 29, 2026, against the Android feature branch and its shared API. This register connects each control objective to a test and a reviewable evidence location. **Tested** means the stated test passed within its stated scope; **partial** means implementation or limited evidence exists; **open** means acceptance evidence is missing or a known failure remains. A passing unit test does not establish deployment effectiveness or regulatory certification.

The API suite was rerun after hardening on October 29: **78 tests passed in six suites**, plus **seven separately executed real-PostgreSQL tests**. The default run intentionally skips those seven opt-in cases. Its sanitized, committed summary is [CONTROL-TEST-RESULTS.json](evidence/CONTROL-TEST-RESULTS.json). The [hardening report][hardening] distinguishes current runs from historical October 20 evidence; the runtime application role itself was not changed by the disposable database tests. The [Validation workflow](../.github/workflows/validation.yml) now defines API/web, PostgreSQL, and Android checks; see [CI validation](CI-VALIDATION.md) for scope and the separate required-check setting. Workflow presence alone does not prove a successful hosted run or protected-branch enforcement. All acceptance tests described as pending are proposals, not completed executions. Use only generated identities, tenant slugs, token fixtures, and document bytes; never publish real records, tokens, signed URLs, private configuration, or raw database/email logs.

## Governance and change management

**GOV-01 — Security baseline and beta scope (partial).** The project records mandatory access, encryption, audit, sensitive-data handling, and beta-scope requirements so implementation decisions can be reviewed against an explicit baseline rather than developer intent. **Test:** review a proposed change against the baseline, reject an out-of-scope workflow, and record any control exception and its resolution; no automated policy-enforcement test currently proves consistent execution. **Evidence:** the versioned [security instructions][baseline], [security debt register][debt], and [security audit record][audit-record] establish the requirements and exception history; the baseline's role list still needs reconciliation with the larger implementation catalogue.

**GOV-02 — Traceable changes and release evidence (partial).** Conventional commits and versioned evidence connect a control change to source, review, and validation without adding percentage tags to commit subjects. **Test:** choose a release candidate, identify its revision, reproduce its build/tests, and reconcile results with that revision; the API run supplies focused evidence, and the [Validation workflow](../.github/workflows/validation.yml) defines repeatable checks. Hosted results must be inspected for the target revision; `main` was confirmed unprotected on October 30, so required-check and peer-approval enforcement remain open. **Evidence:** [commit-message policy][commit-policy], [API test summary][test-summary], [October 20 execution report][execution], API [package scripts][api-package], and Android [build guide][android-guide]. Maintainer assertions or a successful local build alone are not approval records.

## Identity and access

**IAM-01 — Token authenticity and intended recipient (partial).** The API configures RS256 verification against Auth0 JWKS and checks the expected issuer and audience before accepting a token, reducing forged-token and token-reuse risk. **Test:** submit locally generated valid, expired, wrongly signed, wrong-audience, and wrong-issuer fixtures; only the intended valid token should reach the handler. This cryptographic integration test is pending: the current MFA suite mocks both JWT verification and JWKS retrieval. **Evidence:** verification options and error handling in [auth.middleware.ts][auth], contrasted with the mocks in [auth.middleware.test.ts][auth-test]; successful MFA tests must not be presented as proof of signature verification.

**IAM-02 — Mandatory MFA policy (tested at unit level).** The API rejects missing/empty authentication-method claims, password-only authentication, and the ambiguous `otp` marker; it accepts the configured `mfa`, `totp`, `fido`, and `fido2` markers. **Test:** the regression suite's password-only, missing/empty-claim, accepted-method matrix, and mixed password/TOTP cases assert either 401 without handler continuation or successful continuation; they passed October 29. **Evidence:** `authMiddleware — MFA enforcement (regression: MOUD-01)` in [auth.middleware.test.ts][auth-test], the allowlist in [auth.middleware.ts][auth], and [test summary][test-summary]. Auth0 factor configuration and an actual second-factor challenge still need device/provider evidence; a generic marker alone does not identify the factor used.

**IAM-03 — Required claims and namespaced precedence (tested, limited scope).** Missing authorization, roles, or tenant claims fail closed, and the mobile MFA parser gives the configured namespaced claim precedence over the root claim. **Test:** API tests assert 401 for a missing header and 403 for missing roles/tenant; Android tests such as `namespacedAmrTakesPrecedenceOverRootAmr` and `rejectsNonArrayNamespacedAmrFailClosed` reject permissive fallback around malformed/restrictive namespaced claims. **Evidence:** [API claim tests][auth-test] and [JWTDecoderJVMTest.kt][android-test] passed October 29; [the current summary][test-summary] records the rerun, with the [October 20 report][execution] retained as historical evidence. API-side precedence/malformed-claim parity needs its own regression cases, not an inference from mobile tests.

**IAM-04 — Server-side role and tier authorization (partial, focused route tests passed).** API guards restrict writes and document access independently of UI visibility. **Test:** [HTTP route tests][route-test] require unauthenticated upload to fail before connecting and Tier 3 upload/document calls to return 403 without S3 activity; these passed October 29. The complete role/route matrix and Tier 5 dual approval remain unverified. **Evidence:** [rbac.ts][rbac], [credential routes][credentials], and [test summary][test-summary]; audit-viewer/alert permissions and the broader role catalogue still need their own operating evidence.

## Tenant boundaries and data exposure

**TEN-01 — Tenant isolation in PostgreSQL (tested restricted-role fixture; runtime exception remains).** Request middleware sets transaction-local tenant context, and credential RLS restricts a non-owner NOSUPERUSER/NOBYPASSRLS role. **Test:** the [real PostgreSQL suite][postgres-test] asserts that role posture, switches synthetic tenants, and proves an unfiltered SELECT returns only the active tenant; it also rejects the other tenant before an upload. **Evidence:** [tenant middleware][tenant], [credential schema][credential-schema], and [test summary][test-summary]. This disposable fixture proves the policy mechanism; the previously observed superuser runtime configuration in the [October 20 report][execution] was not changed or revalidated as safe.

**TEN-02 — Upload transaction scope and connection hygiene (tested for upload; partial elsewhere).** Upload ownership and metadata use one request connection, lock the credential row before S3, and await database COMMIT before returning success; finalization releases once and error responses roll back. **Test:** [HTTP tests][route-test] cover missing rows, failed updates/commits, and release behavior; a deferred constraint trigger in the [PostgreSQL suite][postgres-test] makes actual COMMIT fail and proves a 500 response with no persisted key. **Evidence:** [tenant middleware][tenant], [credential routes][credentials], and [hardening report][hardening]. Other write handlers retain finish-time commits; S3/database distributed atomicity and general interleaved-request cleanup remain separate risks.

**DATA-01 — Minimum-necessary response contract (tested projection and Tier 3 masking).** Credential lists use an explicit response allowlist and boolean `has_document`, never a raw storage key; web and Android models consume that contract. **Test:** [HTTP tests][route-test] assert true/false presence, removal of injected extra fields/storage keys, and masking of provider name, SSN, DOB, and license number for Tier 3; the [PostgreSQL suite][postgres-test] confirms the actual SQL-derived boolean. **Evidence:** [credential routes][credentials], [rbac.ts][rbac], [test summary][test-summary], and [hardening report][hardening]. Tier 4 still receives selected sensitive fields the mobile display omits, so tighter field-level minimization remains a design question.

**DATA-02 — Timed display concealment (partial).** The web component starts sensitive cells concealed, reveals them on request, and hides them after eight seconds or loss of focus to reduce incidental screen exposure. **Test:** with a synthetic value and fake timers, assert initial concealment, reveal, timeout/blur concealment, and that a server-restricted value cannot be revealed; no component test currently supplies that evidence. **Evidence:** [PhiRevealCell.tsx][reveal] implements the behavior and explains its limits: the authorized value already exists in client memory/network responses, so the timer is not an access boundary. A dedicated audited reveal endpoint and explicit no-store response policy remain pending.

**DATA-03 — Sensitive field encryption at rest (open).** The baseline requires encryption of stored sensitive data, but the credential SSN field remains plaintext in the SQL schema. **Test:** a future encryption test must write a generated value, demonstrate that stored bytes do not contain it, deny unauthorized decryption, and verify authenticated encryption fails after tampering; this is not implemented or proven. **Evidence:** [credential schema][credential-schema] and the SSN entry in [SECURITY_DEBT.md][debt]. Until controlled KMS-backed encryption and migration are validated, synthetic-only use is a release restriction; S3 document encryption does not close this database-field gap.

## Accountability and auditability

**AUD-01 — Fail-closed sensitive-read auditing (tested route and database gates).** Credential lists await every read-audit write before emitting any records, and document reads await audit before signing a URL. **Test:** [HTTP tests][route-test] fail both the first and a later list audit and require an entirely empty-of-records 500 response; the [PostgreSQL suite][postgres-test] revokes actual audit INSERT permission and proves list/document refusal and no signing. **Evidence:** [audit helper][audit-code], [credential routes][credentials], and [test summary][test-summary]. Audit rows use `user_id, tenant_id, action_type, resource_id, occurred_at, ip_address, http_status`, with `GET:credential`/`GET:credential_document`; delivery gates do not establish retention or immutability.

**AUD-02 — Audit of successful mutations (partial; alert outcome visibility tested).** The mutation middleware attempts an attributed audit INSERT after successful authenticated writes. Alert runs additionally report delivery and audit separately: a delivered message with a failed audit returns `emailed: true`, `audited: false`, a fixed error code, and `completed_with_errors`. **Test:** [alert-route tests][alert-test] inject an audit failure after a mocked successful send and assert those fields, retained deduplication attempts, correct counters, and no raw error disclosure; send and tracking failures are also covered. Durable retry or atomic failure of the business operation remains unproven. **Evidence:** [audit middleware][audit-code], [alert routes][alert-routes], and [test summary][test-summary]. General mutation auditing still runs after response finish on a separate pool operation; explicit partial-failure reporting is not an atomic audit guarantee.

**AUD-03 — Append-only audit storage and least privilege (partial; configuration exception).** The audit migration revokes writer privileges and grants INSERT plus sequence access, aiming to prevent application users modifying historical events. **Test:** under the actual runtime role, require audit INSERT to succeed and UPDATE/DELETE to fail; October 20 catalog checks confirmed the restricted writer lacks mutation privileges but also found the configured superuser can alter audit records. **Evidence:** [audit-table migration][audit-schema] and [dated privilege findings][execution]. No WORM store, owner-resistant immutability, or privileged-administrator tamper protection has been demonstrated; a grant declaration is not proof that the deployed connection uses it.

**AUD-04 — Restricted audit viewing (partial).** The audit feed requires Tier 4+, constrains rows to the transaction tenant, and parameterizes filtering and pagination to support accountable review without cross-tenant disclosure. **Test:** prove Tier 3 denial, Tier 4 access only to its synthetic tenant's events, safe filter handling, and bounded pagination; no dedicated route suite currently proves this matrix. **Evidence:** [audit.routes.ts][audit-routes] contains the WHERE/filter/limit logic; [October 20 findings][execution] show the restricted writer cannot SELECT the table at all. Correct that access gap together with tenant-scoped audit permissions rather than granting unrestricted read access to an unprotected table.

**AUD-05 — Retention and recoverability (open).** The project specifies at least six years of audit retention so investigation evidence survives beyond routine application use. **Test:** verify an approved retention policy, attempt prohibited early deletion/expiration in an isolated environment, and restore a synthetic historical audit sample from backup; none of those operational tests is recorded. **Evidence:** the requirement is in the [security baseline][baseline] and [audit middleware comments][audit-code]; there is no versioned retention/archive/restore workflow or retained execution artifact demonstrating six-year enforcement. This is a governance requirement awaiting operating evidence, not a completed retention control.

**AUD-06 — Failed-access detection (open).** Denied authentication, insufficient permissions, and cross-tenant access attempts need safe, attributable security events so probing can be investigated without logging submitted tokens or sensitive values. **Test:** generate synthetic 401/403 requests and cross-tenant denials, then require a sanitized outcome/reason, server timestamp, correlation identifier, and authenticated identity only where trustworthy; no such test or event-delivery proof exists. **Evidence:** [auth middleware][auth], [RBAC guards][rbac], and [audit middleware][audit-code] show response denials but no corresponding denial-event path; the mutation logger covers only successful responses and read helpers cover successful reads. Successful-operation logs do not supply this detection evidence.

## Document handling

**DOC-01 — Content-based upload validation (tested at unit level).** Accepted PDF/PNG/JPEG declarations must match their detected file signatures, reducing reliance on a caller-supplied MIME type. **Test:** `validateUpload` rejects disguised scripts, mismatched declared/detected types, unsupported bytes, empty/truncated content, and buried signatures, while accepting permitted synthetic byte fixtures; these tests passed October 29. **Evidence:** [validator.ts][validator], [validator.test.ts][validator-test], and [test summary][test-summary]. Signature checks are an allowlist control, not malware scanning or proof of a fully valid document; deeper parsing/scanning and endpoint enforcement are separate assurance questions.

**DOC-02 — Upload size and resource limits (tested single-request limit).** Multer caps an in-memory multipart file at 10 MiB. **Test:** the original constant test and the new [HTTP oversized-file test][route-test] pass; a generated file one byte over the limit returns 413 before S3 and receives the no-store policy. **Evidence:** [validator.ts][validator], [validator.test.ts][validator-test], [credential routes][credentials], and [HTTP error middleware][http-middleware]. This proves rejection of an oversized individual upload. Per-IP request throttling is now covered separately by the `rate-limit` regression suite (n+1 request returns 429, `/alerts` carries a tighter budget, `/health` is exempt), but concurrency resilience and total memory bounds under many simultaneous uploads remain unproven, and the limiter is in-process rather than shared across replicas.

**DOC-03 — Non-identifying document names (tested request construction).** Upload keys use tenant/credential identifiers, a random identifier, and an extension derived from content rather than the original filename. **Test:** [HTTP tests][route-test] submit a generated identifying filename, inspect the mocked S3 command, and prove the persisted key has the expected generated form without that filename; the original extension-contract tests also pass. **Evidence:** [credential routes][credentials], [validator.test.ts][validator-test], and [test summary][test-summary]. Actual cloud logging/metadata policy remains unverified; raw keys are now excluded from upload/list responses as well as model serialization.

**DOC-04 — Customer-managed document encryption (partial).** Upload requests specify SSE-KMS and a configured customer-managed key reference to protect stored document objects. **Test:** capture the constructed PutObject request and assert its encryption/key settings, then use a synthetic object to verify stored encryption metadata and denial to an unauthorized decrypt principal; the new [HTTP tests][route-test] assert the SSE-KMS request flag, while configured-key enforcement and cloud tests remain pending. **Evidence:** `ServerSideEncryption`/`SSEKMSKeyId` in [credential routes][credentials] and storage guidance in [s3.ts][s3]. The current signed-URL unit tests do not test uploads, bucket encryption enforcement, IAM/KMS key policy, or key lifecycle controls, and this repository does not contain a cloud-policy execution artifact proving them.

**DOC-05 — Authorized, time-bounded document retrieval (tested helper and route; cloud expiry pending).** A tenant/tier check and successful read audit precede signing, with a maximum five-minute helper TTL. **Test:** [signing tests][s3-test] pin bucket/key/GET/expiry parameters; [HTTP tests][route-test] prove denial for unowned IDs, Tier 3, missing documents, and audit failure; the [PostgreSQL suite][postgres-test] proves retrieval after committed upload and refusal after actual audit-permission revocation. **Evidence:** [s3.ts][s3], [credential routes][credentials], and [test summary][test-summary]. Signing remains mocked; actual cloud expiration/reuse behavior and a signed URL's bearer-risk are not validated by these tests.

## Native client controls

**NET-01 — Encryption and certificate validation in transit (open for deployment assurance).** The baseline requires TLS 1.3 for connections carrying application data; a URL beginning with HTTPS or an SDK default does not prove the negotiated protocol, certificate checks, or protection of database/mail connections. **Test:** against a synthetic deployment, reject older protocol versions and invalid certificates on each applicable hop, record sanitized negotiated-protocol results, and review terminator/provider settings; no such deployment test or configuration artifact is recorded here. **Evidence:** the [security baseline][baseline], [server startup][server], [database client][db], and [S3 client][s3] identify the requirement and connection boundaries; MOB-03 proves a different, narrower property.

**MOB-01 — SDK-managed native OAuth (partial).** Auth0's native SDK owns authorization-code/PKCE, browser launch, protocol state, and callback handling, avoiding duplicated protocol code in the app. **Test:** on an emulator/device with a dedicated test account, complete login and challenge, cancel login, attempt callback/state substitution, and verify only a valid SDK callback creates a session; no recorded instrumentation/E2E test proves this sequence. **Evidence:** [Auth0Client.kt][mobile-auth], [Android manifest][manifest], and [Android configuration guide][android-guide]. Historical compilation and MFA-claim unit tests validate different properties and must not be cited as proof of the browser/protocol exchange.

**MOB-02 — Encrypted credentials and session lifecycle (partial).** `SecureCredentialsManager` encrypts stored tokens using Android Keystore support, renews credentials, and clears local credentials before best-effort refresh-token revocation/browser logout; app backup is disabled. **Test:** on a test device, inspect private storage for absence of plaintext token fixtures, verify expiry/renewal, logout/restart, failed renewal, and device-specific key backing; these device tests are pending. **Evidence:** [dependency providers][mobile-di], [Auth0Client.kt][mobile-auth], [manifest][manifest], and [session ViewModel][auth-vm]. Hardware backing depends on the device, and successful local logout does not prove remote revocation succeeded.

**MOB-03 — Restricted development cleartext exception (partial).** The Android debug source set allows cleartext only to the emulator host alias, while the base configuration rejects it for other hosts and release excludes that overlay. **Test:** inspect merged debug/release manifests, prove synthetic HTTP to the emulator alias works only in debug, and prove another HTTP destination/release request fails; only historical merged-debug-manifest/build inspection is recorded. **Evidence:** [debug manifest][debug-manifest], [network security XML][network-config], and [October 20 build record][execution]. This controls cleartext exceptions; it does not establish the baseline's separate TLS 1.3 requirement across API, Auth0, S3, database, and mail connections.

## Operations and secure development

**OPS-01 — Minimum-necessary alert payload (tested service boundary; delivery assurance partial).** The email service rejects unknown template fields and requires an opaque UUID and valid calendar date, then projects only `credentialId`/`expirationDate`; no optional name field or shallow denylist remains. **Test:** [mail tests][mail-test] capture the mocked provider call and reject extra/name fields, nested values, missing fields, invalid UUIDs, and invalid dates before sending, including a valid leap-day case. **Evidence:** [email.service.ts][email], [alert routes][alert-routes], and [test summary][test-summary]. No real email is sent; template content, recipient governance, transport, provider agreements, and generic-notification policy still require separate evidence.

**OPS-02 — Scheduled expiration monitoring and duplicate suppression (partial).** The server selects unexpired credentials within a configured window and records `last_alerted_at` after a successful send, supporting renewal oversight. **Test:** with a controlled clock and mail stub, verify date boundaries, two successive runs, a failed send, renewal, and concurrent workers; these tests are pending, and the missing renewal reset is a known gap. **Evidence:** [expiration service][expiration], [scheduler][scheduler], and [alert routes][alert-routes]. The scheduler currently uses one configured tenant, and send/mark are not an exactly-once transaction; overlapping runs can duplicate delivery. Source comments alone do not establish execution time or scheduler reliability.

**OPS-03 — Safe API errors and operational detection (tested redaction; monitoring partial).** The global error handler returns fixed messages and never logs raw error objects or stacks, including in development; known parser/upload-size errors receive fixed 400/413 responses. **Test:** [HTTP tests][route-test] inject synthetic sensitive error sentinels through driver/S3 failures and malformed JSON, then assert generic responses, no-store headers, and no sentinel in captured logs. **Evidence:** [server.ts][server], [HTTP middleware][http-middleware], and [hardening report][hardening]. Alert callers also suppress raw provider errors; correlation identifiers, denied-access events, alert delivery, and incident-response effectiveness remain unproven.

**OPS-04 — Dependency readiness and safe degraded responses (tested health failure; recovery partial).** Startup checks PostgreSQL before listening, and the health endpoint reports connected/degraded status without database details. **Test:** [HTTP tests][route-test] force a health-query failure, require 503 without the injected sentinel/detail field, verify no-store, and confirm connection release. **Evidence:** [server.ts][server], [db.ts][db], and [test summary][test-summary]. Startup failure injection, monitor integration, response-time objectives, and recovery drills are still pending; this test establishes the health-handler failure path rather than overall service availability.

**SDLC-01 — Configuration and repository hygiene (partial).** Ignore rules separate secrets, local SDK settings, signing material, generated artifacts, and portfolio drafts from application source. **Test:** use `git check-ignore` with fabricated `.env`, `local.properties`, and signing-file paths, then scan tracked files and history using an approved secret scanner; no secret-scanner workflow/result is recorded, and ignore rules cannot remove an already tracked secret. **Evidence:** [.gitignore][ignore], configuration access in [Android build configuration][android-build], and the [commit-message policy][commit-policy]. Publish only approved aggregate test results; raw application logs, credential files, settings backups, and Git recovery bundles stay outside repository evidence.

**SDLC-02 — Controlled database schema changes (partial; known failure).** Raw SQL migrations are explicitly ordered and tracked by filename to support reviewable changes and replay avoidance. **Test:** run fresh-schema, already-applied-schema, repeated-DDL, interrupted-tracking, and concurrent-runner cases; October 20 isolated tests found CEU DDL replay succeeds but the baseline rename fails with `42703`, and runner recovery/concurrency remains untested. **Evidence:** [migration runner][migrations], [rename migration][rename], and the dated [execution report][execution]. File DDL and its tracking INSERT are not one atomic transaction; modifying an already-recorded file is not a reliable upgrade mechanism.

**SDLC-03 — Separation of development-only seeding (partial).** The credential seed endpoint is omitted when the API starts in production mode; outside production it still requires authentication, Tier 4 access, and mutation auditing. **Test:** start isolated test applications under production and development settings, require production to return 404 for the seed path, and verify lower-tier denial plus attributed synthetic insertion in development; the current suite does not include these route-registration tests. **Evidence:** the environment guard and seed middleware chain in [credential routes][credentials] document the intended boundary. A client-side development flag is not evidence of server enforcement, and deployment environment configuration must also be verified.

**SDLC-04 — Dependency and build-input integrity (partial).** A single versioned root-workspace npm lockfile — the duplicate `apps/api` lockfile was removed, so an audit cannot be run against a stale tree — and a checksum-pinned Gradle wrapper provide reviewable build inputs and a check against an altered Gradle distribution. **Test:** reproduce the build from those inputs, reject a test distribution with a mismatching checksum, and run an approved vulnerability/dependency review with findings triaged; historical Android build success does not prove the mismatch or vulnerability-management cases, which have no recorded results here. **Evidence:** [package-lock.json][npm-lock], [Gradle wrapper properties][wrapper], [API package scripts][api-package], and [Android build configuration][android-build]. Locked versions and passing functional tests do not establish that dependencies are current or vulnerability-free.

**CEU-01 — Education-record integrity and verification (open; separate branch).** The proposed CEU schema records course credits, issuer references, and verification state to support accountable renewal decisions, but it is not a completed API/mobile workflow on this branch. **Test:** reject cross-tenant parent references, require authorized verification with an audit event, preserve history, and compute compliance against agreed credential-specific credit/cycle rules; October 20 synthetic probing instead accepted a cross-tenant reference. **Evidence:** the [CEU review][execution] identifies the separate migration branch, single-column foreign keys, deletion behavior, and simplified 24-month assumption. Local schema presence and verification fields do not prove tenant integrity, board verification, or compliant renewal decisions.

## Reproducing and maintaining evidence

From `apps/api`, run `npm test -- --runInBand --json --outputFile=coverage/hardening-results.json`, then the opt-in PostgreSQL runner described in [the hardening report][hardening]. After the Android run, `node scripts/write-control-evidence.cjs` regenerates the aggregate using a fixed path allowlist and source hashes; raw runner files are intentionally ignored. Review the aggregate before publishing. Android commands and local XML report locations are documented in the [module guide][android-guide] and [execution record][execution]; retain the recorded date when reusing historical evidence. For cloud/device/route tests, add a versioned synthetic test and sanitized result before upgrading a control's status. A change to source, runtime role, key policy, identity-provider configuration, or deployment can invalidate prior evidence.
